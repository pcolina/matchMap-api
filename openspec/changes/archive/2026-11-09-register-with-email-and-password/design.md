# Design

## Context

Registration is implemented in `RegistrationService`, which takes a `RegisterInput` record with `email`, `username`, `displayName` and `password`. Username validation lives in the nested `Registration` record (`[a-z0-9_]{3,30}`). The `User` type and the `UserAccount` entity both carry `displayName`, and the `display_name` column in `user_account` is `NOT NULL` (migration `V2__create_user_accounts.sql`, which is applied and must not be edited).

Google sign-in already creates accounts without a client-supplied username: `GoogleAccountService` calls `UsernameGenerator.generate(email, accounts::existsByUsername)`, and that generator is the existing rule for username derivation.

The contract is the source of truth (`contracts/graphql/account.graphqls`). The schema changes first, then the implementation follows.

## Goals / Non-Goals

**Goals:**
- `register` accepts only `email` and `password`.
- The `User` type has no `displayName`; the username is the identifier the client sees.
- Username is generated by the backend from the email and is unique.

**Non-Goals:**
- Client code, codegen and the registration page (see proposal.md, Out of scope).
- Changing sign-in, the password policy's rules, or the error codes already merged in #9 and #10.
- Rewriting existing usernames.

## Decisions

- **Contract first.** `RegisterInput` loses `username` and `displayName`; `User` loses `displayName`; the `register` description is updated. The contract test reads the file, so it is written before the schema change.
- **One username generator for both paths.** `UsernameGenerator` takes the source text (the email prefix for registration, the Google profile name for Google sign-in) and applies the same sanitization, `user_` rule and `_<n>` suffix from 2. Registration and Google sign-in cannot diverge.
- **Password error code is `PASSWORD_INVALID`.** The password `@Size`/`@Pattern` violations map to `PASSWORD_INVALID` with `extensions.field` `password`, instead of `VALIDATION_FAILED`. The mapping lives in `AccountException` and `RegistrationService.validate`.
- **Fields that no longer exist.** A client that sends `username` or `displayName` in `register` gets a GraphQL validation error, because the input type has no such field. This is the default behavior of the GraphQL layer and needs no custom code.
- **The `display_name` column is dropped.** A new append-only migration `V3__drop_display_name.sql` runs `ALTER TABLE user_account DROP COLUMN display_name`. `UserAccount` and every constructor call lose the `displayName` argument.

## Risks / Trade-offs

- [Risk] Existing clients still send `username` or `displayName` → Mitigation: the contract change is breaking and is recorded as **BREAKING** in proposal.md. The clients are in other repositories and the MVP is not deployed.
- [Risk] Generated usernames collide under concurrent registration → Mitigation: the database already has a unique constraint on `username` (`uk_user_account_username`), and `RegistrationService` already maps the constraint violation to an error.
- [Risk] Dropping `display_name` loses the stored names of existing accounts → Mitigation: the name is no longer part of the API, and the decision to drop it is explicit. Existing usernames are not changed.

## Migration Plan

- If a migration is chosen, it is a new append-only file after `V2__create_user_accounts.sql`. The applied migrations are not edited.
- Rollback: the contract change is reverted in the same commit series as the code. No data is removed unless the drop-column option is chosen.
